  Current Architecture

  The event system uses an object-oriented consumer pattern:

  1. ParticleEventConsumerType (src/Solution/ParticleTracker/Particle/Events/ParticleEvents.f90:10-13) - abstract base type with deferred handle_event procedure
  2. ParticleEventDispatcherType (src/Solution/ParticleTracker/Particle/Events/ParticleEvents.f90:15-21) - maintains a list of consumers
  3. ParticleTracksType (src/Solution/ParticleTracker/Particle/ParticleTracks.f90:80) - extends the consumer type and implements event handling

  Conversion Difficulty: Moderate to Difficult

  Converting to procedure pointers would face a significant architectural challenge: the current consumer pattern provides essential state management that would be difficult to replicate with simple procedure pointers.

  The Core Problem

  ParticleTracksType carries substantial state:
  - Track files array with metadata (unit numbers, CSV vs binary, PRP association)
  - Event selection flags (which event types to track)
  - Output unit for logging
  - Multiple helper methods (should_save, should_log, is_selected, expand_files)

  Proc Pointer Challenges

  A pure procedure pointer approach would require:

  1. No natural state storage - procedure pointers can't encapsulate data like objects can
  2. Manual context passing - you'd need to pass all state explicitly to each callback or use module-level variables (problematic for multiple instances)
  3. Loss of encapsulation - helper methods like should_save and is_selected would need to become standalone procedures

  Possible Hybrid Approach

  You could use a hybrid pattern:

  type :: CallbackWrapperType
    ! State members
    integer(I4B) :: iout
    type(ParticleTrackFileType), allocatable :: files(:)
    ! ... other state ...

    ! Procedure pointer
    procedure(callback_interface), pointer, nopass :: callback => null()
  end type

  But this essentially recreates what you have now, just with procedure pointers instead of type-bound procedures. The complexity remains similar.

  Recommendation

  Keep the current consumer type system because:
  - Clean state encapsulation (each consumer manages its own data)
  - Extensible (easy to add new consumer types)
  - Type-safe with compile-time checking
  - The polymorphic dispatch overhead is negligible compared to I/O operations

  The only advantage of procedure pointers (slight performance improvement) is irrelevant here since the bottleneck is file I/O, not the dispatch mechanism.

  Design Options for Mixed Semantics

  Here are the main approaches, from simplest to most flexible:

  Option 1: Two Dispatch Methods

  Keep one dispatcher, but provide two dispatch modes:

  ! All callbacks return boolean
  logical function event_callback(context, particle, event)

  ! In ParticleEventDispatcherType
  logical function dispatch_claim(this, particle, event) result(claimed)
    ! Stop at first .true., return whether any claimed

  subroutine dispatch_broadcast(this, particle, event)
    ! Call all subscribers, ignore/validate return values

  Pros: Simple, explicit at call site, single subscription list
  Cons: Observers waste cycles returning .false.

  Option 2: Separate Subscription Types

  Track handlers vs. observers separately:

  type :: ParticleEventDispatcherType
    type(ListType) :: handlers     ! can claim events
    type(ListType) :: observers    ! always notified
  contains
    procedure :: subscribe_handler
    procedure :: subscribe_observer
    procedure :: dispatch  ! tries handlers first, then notifies observers

  Pros: Clear intent, efficient (observers never checked for claiming)
  Cons: More methods, need to choose at subscription time

  Option 3: Subscription Metadata

  Add flags to subscriptions:

  type :: ParticleEventSubscription
    procedure(event_callback), pointer, nopass :: callback
    class(*), pointer :: context
    logical :: can_claim    ! can this subscriber claim events?
    integer :: priority     ! for ordering (optional)
  end type

  ! dispatch tries can_claim=.true. first (stops on acceptance),
  ! then notifies can_claim=.false. subscribers

  Pros: Very flexible, single subscription method
  Cons: More complex, dispatch logic more intricate

  Option 4: Event-Specific Dispatch

  Encode semantics in event types:

  type, abstract :: ParticleEventType
    logical :: claimable = .false.  ! or use inheritance

  type, extends(ParticleEventType) :: BoundaryReachedEvent
    logical :: claimable = .true.

  Pros: Self-documenting, dispatch behavior tied to event nature
  Cons: Couples event types to dispatch mechanism

  Option 5: Separate Dispatchers

  One for internal (claimable), one for external (broadcast):

  type(ParticleEventDispatcherType), pointer :: boundary_events  ! claimable
  type(ParticleEventDispatcherType), pointer :: status_events    ! broadcast

  Pros: Complete separation, simplest implementation
  Cons: Managing multiple dispatchers, where does tracks subscribe?

  My Recommendation

  I'd suggest Option 2 (Separate Subscription Types) because:

  1. Intent is clear: When subscribing an exchange, you call subscribe_handler; for output, subscribe_observer
  2. Efficient: No wasted boolean returns from observers
  3. Extensible: Easy to add more patterns (e.g., priority handlers)
  4. Single call site: Just dispatch() - it handles both lists internally

  ! Exchanges
  call this%boundary_events%subscribe_handler(exchange_handle_boundary, p)

  call this%events%subscribe_observer(tracks_handle_event, p)

● Yes, Option 1 is a reasonable pattern, though I'd say it's more common to see the underlying semantics (broadcast vs. claim) than this specific API design. Let me put it in context:

  Common Patterns in Event Systems

  Pure broadcast (most traditional event systems):
  - JavaScript EventEmitter, C# events, Java observers
  - Fire-and-forget, no acknowledgment
  - What you had initially

  Stoppable propagation (very common in UI/middleware):
  - DOM event bubbling (event.stopPropagation())
  - Express.js middleware (handlers can choose to call next() or not)
  - Returns/flags indicate "I handled it, stop here"

  Chain of responsibility (classic design pattern):
  - Handlers return whether they handled the request
  - First handler to return true stops the chain
  - Exactly what you need for exchanges

  Is Having Multiple Dispatch Methods Standard?

  The specific API of having dispatch_claim() vs. dispatch_broadcast() is less common but totally valid. More often you see:

  Single method with flags:
  call dispatch(event, stop_on_claim=.true.)

  Single method, behavior from event properties:
  type :: EventType
    logical :: stoppable = .true.

  Return value conventions (middleware):
  accepted = dispatch(event)  ! always returns, caller decides what to do

  Why Option 1 is Good Here

  Your intuition is right - it's natural because:

  1. Explicit intent: Call site makes semantics obvious
  2. Type safety: Compiler ensures you handle the return value for dispatch_claim
  3. Simple: No need to configure events or subscriptions with flags
  4. Fortran-friendly: Subroutine vs. function is a clear distinction

  This is similar to how Fortran's I/O system has different forms for different needs (read, inquire, backspace, etc.) rather than a single generic call with flags.

  So yes, go with Option 1. It's pragmatic, clear, and easy to implement. The pattern itself (supporting both semantics) is definitely standard, even if the exact API design varies across frameworks.
