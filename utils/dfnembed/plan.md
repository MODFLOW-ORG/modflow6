# Spec reproduction plan — MF6 / flopy4

> **Scope:** This document covers the MF6 binary (`mf6 --spec`) and its
> integration with flopy4 as the primary downstream consumer. The companion
> devtools work — adding `DfnSpec.dump()` to `modflow_devtools` to enable a
> TOML output format — is tracked separately in
> `../modflow-devtools/dfnspec-plan.md`.

## Motivation

Tooling that wraps MF6 (e.g. flopy4) would benefit from an authoritative,
version-aware copy of the input spec. Today we fetch DFN files from the
MF6 source repo on demand. We cannot prove that a given set of DFNs, or
a `flopy.mf6` module generated from them, matches any given MF6 binary.

An ideal long-term solution is probably runtime serialization (emitting
an internally-generated spec), but that will require substantial IDM work.
A tractable first step is **verbatim embedding**: bundle the raw DFN text
into the binary at build time and expose it via a new `--spec` CLI option.

```bash
mf6 --spec > mf6io.toml   # dump to file
mf6 --spec | flopy4 sync  # pipe to tooling
```

The spec and binary become a single artifact, version alignment becomes
structurally guaranteed, and flopy code-generation works offline.

|------|------|-------|
| 1 | Jinja template for the Fortran spec module | `utils/idmloader/templates/DfnSpec.f90.jinja` |
| 2 | Spec generation added to existing `dfn2f90.py` | `utils/idmloader/scripts/dfn2f90.py` |

| 4 | New `--spec` flag in CLI argument handler | `src/Utilities/comarg.f90` |
| 5 | Meson installation test | `meson.build` (top-level) |

The generated source file (`DfnSpec.f90`) **is committed** to
`src/Utilities/` alongside other source files. This follows the same
pattern as the IDM files in `src/Idm/`, which are also generated by
`dfn2f90.py` and committed.

This follows the same pattern as `utils/idmloader`, which uses Jinja
templates and a Python render script to generate the IDM input-definition
modules. The key difference is that here we do **no DFN parsing** — spec
generation is raw text I/O only.

DFN files will continue to be shipped with MF6 releases during a
transition period. Once downstream tools (flopy4, devtools) fully migrate
to `mf6 --spec`, the case for dropping bundled DFNs can be revisited.

## Step 1 — Jinja template: `utils/idmloader/templates/DfnSpec.f90.jinja`

Template lives alongside the existing idmloader templates.

```jinja
! ** Do Not Modify! MODFLOW 6 system generated file. **
module DfnSpecModule
  use, intrinsic :: iso_fortran_env, only: output_unit
  implicit none
  private
  public :: write_spec

contains

  subroutine write_spec()
{% for dfn in dfns %}
    write(output_unit, '(a)') '# --- {{ dfn.name }} ---'
{% for line in dfn.lines %}
{{ line | spec_line }}
{% endfor %}
    write(output_unit, '(a)') ''
{% endfor %}
  end subroutine write_spec

end module DfnSpecModule
```

**Key design choices:**

- **`output_unit` not `istdout`**: `istdout` (defined in `SimVariablesModule`)
  defaults to `output_unit` but is redirected to `mfsim.stdout` when `--silent`
  is active. Using `output_unit` directly ensures `--spec` always writes to the
  real stdout, regardless of what other flags are combined with it. The
  subroutine therefore takes no unit argument.
- **One `write` call per source line** — avoids Fortran parameter-array size
  limits and keeps the generated file cleanly diffable.
- **`# --- <name> ---` sentinel** before each file's content. This is a legal
  DFN comment (`#` lines are ignored by all existing parsers), so bare-DFN
  consumers are unaffected; tooling that needs per-file boundaries can split on
  the sentinel.
- **Blank `write` after each file's block** gives a visual gap and a clean
  split point for line-oriented parsers.
- **`spec_line` Jinja filter** (see Step 2) handles single-quote escaping and
  line continuation for DFN lines exceeding the 132-char Fortran source limit.

### Why not a `parameter` array?

A `character(len=N), parameter :: lines(M)` holding ~927 KB of DFN text would
exceed Fortran string-literal limits and create a source file that stresses
compilers. Procedural `write` calls are idiomatic for large generated output
and compile reliably.

### Long DFN lines

The longest line across all DFN files is ~1650 characters (description text).
Lines that would make the Fortran source line exceed 132 characters are split
using `advance='no'` write chunks in the `spec_line` filter; the final chunk
uses the standard write to emit the newline.

### `common.dfn`

`common.dfn` is a special file containing shared variable descriptions
referenced by `REPLACE` directives in other DFNs. It lives in the same DFN
directory and is included verbatim in the output (sorted filename order puts it
between `chf-zdg.dfn` and `exg-chfgwf.dfn`). Consumers need it to interpret
the `REPLACE` directives in other DFN files; including it unchanged is correct.

## Step 2 — Spec generation in `utils/idmloader/scripts/dfn2f90.py`

Spec generation is added directly to `dfn2f90.py` — no new script, no new
CLI flag. The `make_spec()` function is called unconditionally at the end of
`make_all()`, so running the script always regenerates both the IDM files and
`DfnSpec.f90`.

New additions to `dfn2f90.py`:

```python
SPEC_PATH = SRC_PATH / "Utilities" / "DfnSpec.f90"

_WRITE_STD = "    write(output_unit, '(a)') "
_WRITE_NO_ADV = "    write(output_unit, '(a)', advance='no') "
_MAX_STD = 132 - len(_WRITE_STD) - 2
_MAX_NO_ADV = 132 - len(_WRITE_NO_ADV) - 2


def _spec_line(s: str) -> str:
    escaped = s.replace("'", "''")
    if len(escaped) <= _MAX_STD:
        return f"{_WRITE_STD}'{escaped}'"
    chunks = []
    while escaped:
        chunks.append(escaped[:_MAX_NO_ADV])
        escaped = escaped[_MAX_NO_ADV:]
    lines = [f"{_WRITE_NO_ADV}'{c}'" for c in chunks]
    lines.append("    write(output_unit, '(a)') ''")
    return "\n".join(lines)


def make_spec(verbose: bool = False) -> None:
    template_env = _get_template_env()
    template = template_env.get_template("DfnSpec.f90.jinja")
    dfns = [
        {"name": p.name, "lines": p.read_text(encoding="utf-8").splitlines()}
        for p in sorted(DFN_PATH.glob("*.dfn"))
    ]
    if verbose:
        print(f"  writing {SPEC_PATH}")
    with open(SPEC_PATH, "w", newline="\n") as f:
        f.write(template.render(dfns=dfns))
```

The `_spec_line` filter is also registered in `_get_template_env()`:

```python
template_env.filters["spec_line"] = _spec_line
```

The spec always embeds ALL `.dfn` files from `DFN_PATH` regardless of
which subset was passed to `make_all()` for IDM generation.

## Step 4 — CLI flag: `src/Utilities/comarg.f90`

### Import

```fortran
use DfnSpecModule, only: write_spec
```

### New case in `select case (trim(adjustl(uctag)))`

```fortran
case ('-SPEC', '--SPEC')
  lstop = .TRUE.
  call write_spec()
```

### `write_usage` (`OPTIONSFMT` string)

```fortran
&' -spec     --spec           Emit embedded DFN input spec to stdout.',/,&
```

**Parallel builds:** `lstop = .TRUE.` is set before `Mf6Initialize` is ever
called, so MPI/PETSc is never initialized. `--spec` is safe in parallel builds
and does not require `mpiexec`.

**`--silent` interaction:** writing directly to `output_unit` inside
`write_spec()` means the spec always goes to real stdout regardless of
whether `--silent` is also present.

## Output format

The stream written to stdout is the raw DFN text for all files in
`doc/mf6io/mf6ivar/dfn/`, concatenated in lexicographic filename order
(`sorted()` in Python), with one sentinel comment line prepended to each file:

```
# --- chf-cdb.dfn ---
# --------------------- chf cdb options ---------------------
...

# --- chf-chd.dfn ---
...

# --- common.dfn ---
...

# --- exg-chfgwf.dfn ---
...
```

Lines are written verbatim (UTF-8, no truncation).

## Future: TOML output format

The current output is raw DFN text — the format MF6 has always used internally,
and the one `modflow_devtools` can already parse. A natural upgrade is to emit a
**single TOML document** representing the full spec, which eliminates the
sentinel/splitting machinery entirely.

### Why a single document, not per-component files

Multiple per-component TOML files require a directory on disk; a single document
can be piped directly:

```bash
mf6 --spec | python -c "import sys, tomllib; spec = tomllib.load(sys.stdin.buffer)"
```

No sentinel parsing, no temp directory, no bridge script.

### Natural schema

The schema falls directly out of `modflow_devtools.dfns.DfnSpec`. `DfnSpec._flat`
is a `{name: Dfn}` mapping; `asdict(dfn)` (already used internally) gives the
per-component dict. The merged document is those dicts keyed by component name
under a top-level `schema_version`:

```toml
schema_version = "2"

["gwf-chd"]
name = "gwf-chd"
advanced = false
multi = true

["gwf-chd".options.auxiliary]
block = "options"
name = "auxiliary"
type = "string"
...

["gwf-dis"]
name = "gwf-dis"
...
```

This is identical to what you'd get by wrapping each existing per-component TOML
(in `doc/mf6io/mf6ivar/dfn/toml/`) under its component name as a top-level
TOML table.

### What's needed

1. **`DfnSpec.dump()` in `modflow_devtools`** — the only new work required on
   the devtools side. See `../modflow-devtools/dfnspec-plan.md` for details.
2. **`make_spec()` reads from `doc/mf6io/mf6ivar/dfn/toml/`** — a one-line
   change on the MF6 side (glob `toml/*.toml` instead of `*.dfn`). The Fortran
   embed and CLI machinery are unchanged.

The per-component TOML files already exist in the repo, so no new conversion
step is needed on the MF6 side once `DfnSpec.dump()` exists in devtools.

### Transition path

The DFN-text embed is the right interim format: it requires no new work in
devtools and `modflow_devtools` already parses it. Once `DfnSpec.dump()` exists,
`--spec` can switch to TOML with no changes to the Fortran CLI or build system —
only `make_spec()` changes. The consumer interface (`mf6 --spec`) remains stable
throughout.

## Future: per-component filtering

A natural follow-on feature would be filtering the spec output to a single
component or package, e.g. `mf6 --spec gwf` or `mf6 --spec gwf-chd`. This
is deliberately deferred for two reasons:

1. **Tooling-side filtering is already sufficient.** The `# --- <name> ---`
   sentinels were designed for exactly this purpose. Any caller can filter with
   a one-liner:

   ```bash
   mf6 --spec | awk '/^# --- gwf-chd/{p=1} /^# --- /{if(!/gwf-chd/)p=0} p'
   ```

2. **The cost is lower after runtime serialization.** Adding filtering now
   would require look-ahead argument parsing in `comarg.f90` (the same pattern
   `--level` uses) and restructuring `DfnSpec.f90` into per-component
   subroutines or a dispatch table — meaningful complexity for a feature
   consumers can already handle themselves. Once `--spec` is backed by live IDM
   introspection (see below), the component structure is already present in the
   data and filtering becomes a trivial extension.

## Future: runtime serialization

This plan embeds a **build-time snapshot** of the DFNs. The long-term direction
is `--spec` emitting MF6's live internal input-definition structures — the
`InputParamDefinitionType` arrays that `utils/idmloader` already generates are
the natural source.

### What changes

- The CLI flag (`--spec`) and output format (DFN text with sentinels, or an
  upgraded schema) stay the same from the consumer's perspective.
- `DfnSpecModule` and `src/Utilities/DfnSpec.f90` are deleted; the call in
  `comarg.f90` is redirected to a new serialization subroutine.
- `utils/idmloader/templates/DfnSpec.f90.jinja` and the `make_spec()` call in
  `dfn2f90.py` are removed.
- No changes needed in flopy4 or devtools — they still pipe `mf6 --spec`.

### Where the data lives

`utils/idmloader` already generates one Fortran module per DFN file (e.g.
`gwf-chdidm.f90`). Each module exposes three public arrays:

```fortran
type(InputParamDefinitionType), target :: gwf_chd_param_definitions(:)
type(InputParamDefinitionType), target :: gwf_chd_aggregate_definitions(:)
type(InputBlockDefinitionType), target :: gwf_chd_block_definitions(:)
```

The `IdmDfnSelector` / `IdmComponentDfnSelector` modules provide a
`getInputDefinition(component, subcomponent)` dispatch mechanism that returns
these arrays for any registered component. A serialization subroutine would
iterate over all registered components, call the selector, and emit DFN-format
text (or a richer format) from the struct fields rather than from embedded
string literals.

### Why this is non-trivial

The `InputParamDefinitionType` and `InputBlockDefinitionType` structs were
designed for the IDM loader, not for round-trip serialization. A few gaps to
be aware of:

- **`REPLACE` directives are resolved at parse time.** `common.dfn` substitutions
  are baked into the longname/description strings stored in the IDM arrays;
  the original `REPLACE` syntax is not preserved. The serialized output would
  therefore differ slightly from the source DFN text (expanded rather than
  templated), which is fine for consumers but worth documenting.
- **Metadata not captured by IDM.** Some DFN header comments (e.g.
  `# flopy multi-package`, `# mf6 subpackage`) are parsed separately and
  stored in fields like `multi_package` and `subpackages` on `DfnFile` at
  code-generation time, but not all of this survives into the compiled IDM
  structs. An audit of what is and isn't round-trippable will be needed.
- **No master component registry at runtime.** The selector modules currently
  require knowing the component/subcomponent strings up front. A `--spec`
  serialization pass needs a way to enumerate all registered components without
  hardcoding the list — this likely means a new thin registration layer or
  extending `IdmDfnSelector` to expose an iterator.

The verbatim embed is therefore not a dead end; it is a correct, shippable
first step on the path to a self-describing simulator, and it keeps the
consumer interface stable while the harder IDM work is done.
